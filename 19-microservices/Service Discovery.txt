Heartbeats in Microservices

A heartbeat is a periodic signal sent by a service instance to the Service Registry to tell it:

"I am still alive and running."

It is commonly used with service registration and service discovery.

1. Why are heartbeats required?

Imagine Payment Service registers itself:

Payment Service
      |
      | Register
      ↓
Service Registry

PAYMENT-SERVICE
→ 10.0.0.5:8080

Later, the Payment Service crashes.

Payment Service ❌

But if the registry still has:

PAYMENT-SERVICE
→ 10.0.0.5:8080

another service might try to call that dead instance.

Heartbeats help the registry detect this.

2. How heartbeat works

After registration:

Payment Service
      |
      | "I'm alive"
      ↓
Service Registry

After some time:

Payment Service
      |
      | "I'm still alive"
      ↓
Service Registry

And again:

Payment Service
      |
      | "I'm still alive"
      ↓
Service Registry

This happens periodically.

For example, conceptually:

Time
 │
 ├── 0 sec  → Register
 ├── 30 sec → Heartbeat
 ├── 60 sec → Heartbeat
 ├── 90 sec → Heartbeat
 └──120 sec → Heartbeat

The exact interval depends on the technology/configuration.

3. What happens when heartbeat stops?

Suppose:

Payment Service
      |
      | Heartbeat ✅
      ↓
Registry

Then the service crashes:

Payment Service ❌

No more heartbeats:

30 sec → ❌
60 sec → ❌
90 sec → ❌

The registry notices that the expected heartbeat has not arrived within its configured timeout.

It can then mark/remove that instance from the available instances.

Before:

PAYMENT-SERVICE
 ├── 10.0.0.5:8080
 ├── 10.0.0.8:8080
 └── 10.0.0.12:8080


After Payment-1 becomes unavailable:

PAYMENT-SERVICE
 ├── 10.0.0.8:8080
 └── 10.0.0.12:8080

Now other services won't normally select the dead instance.

4. Heartbeat is not the same as health check

This is an important interview distinction.

Heartbeat

The service tells the registry:

"I am alive."
Service ─────────→ Registry
          heartbeat
Health check

The registry/load balancer/orchestrator checks the service:

Registry/Load Balancer
          |
          | "Are you healthy?"
          ↓
       Service
          |
          ↓
        UP/DOWN

So:

Heartbeat = service pushes an "I'm alive" signal.

Health check = infrastructure actively checks the service.

Depending on the technology, the terms and mechanisms can overlap, so don't assume every platform uses both independently.

5. Heartbeat in Service Discovery

The complete lifecycle can be:

        Service starts
             ↓
       Service Registration
             ↓
       Registry stores it
             ↓
          Heartbeats
             ↓
     Instance remains available
             ↓
      Service crashes/stops
             ↓
       Heartbeats stop
             ↓
   Registry detects timeout
             ↓
 Instance marked unavailable
6. Example with 3 instances

Initially:

PAYMENT-SERVICE

Payment-1 → 10.0.0.5:8080  ✅
Payment-2 → 10.0.0.8:8080  ✅
Payment-3 → 10.0.0.12:8080 ✅

Each instance sends heartbeats:

P1 → Registry ❤️
P2 → Registry ❤️
P3 → Registry ❤️

Now P2 crashes:

P1 → Registry ❤️
P2 → ❌
P3 → Registry ❤️

After the configured timeout:

PAYMENT-SERVICE

Payment-1 → 10.0.0.5:8080  ✅
Payment-2 → removed/unavailable ❌
Payment-3 → 10.0.0.12:8080  ✅

A client can now use P1 or P3.

7. Heartbeat and service lookup together

Suppose Order Service performs a lookup:

Order Service
      |
      | Lookup PAYMENT-SERVICE
      ↓
Service Registry

The registry should ideally return currently available instances:

Payment-1 → ✅
Payment-3 → ✅

rather than:

Payment-2 → ❌

Heartbeats help maintain the registry's knowledge of instance availability.

8. What if the network temporarily fails?

This is where things become more interesting.

Suppose Payment Service is actually running:

Payment Service → RUNNING ✅

but its network connection to the registry is broken:

Payment Service ──X── Registry

The registry stops receiving heartbeats.

From the registry's perspective, the instance may become unavailable after the configured timeout.

This is why heartbeat-based systems have to deal with temporary network failures and false failure detection.

9. Heartbeat vs registration

Don't confuse these:

Registration

Happens when the service joins the registry:

Service → Registry
"I am PAYMENT-SERVICE at 10.0.0.5:8080."
Heartbeat

Happens periodically afterward:

Service → Registry
"I'm still alive."

So:

Registration = "Here I am."

Heartbeat = "I'm still here."
10. Heartbeat vs health check vs service lookup

You should be able to explain all three:

Registration
    ↓
"I am here."

Heartbeat
    ↓
"I'm still alive."

Health Check
    ↓
"Are you healthy?"

Service Lookup
    ↓
"Where is that service?"
⭐ Interview answer

A heartbeat is a periodic signal sent by a service instance to a service registry to indicate that the instance is still alive. If the registry stops receiving heartbeats within a configured timeout, it can consider the instance unavailable and prevent it from being returned for service discovery or used for traffic routing.

One-line memory trick

Registration → "I am here"
Heartbeat → "I am still here"
Lookup → "Where is it?"
Health check → "Is it healthy?"

Self-preservation mode  
Eureka Self-Preservation Mode

Self-preservation mode is a safety mechanism in Eureka Server that prevents Eureka from aggressively removing service instances when it suspects that many instances have stopped sending heartbeats.

Why is it needed?

Imagine Eureka has 100 registered instances:

Eureka
  |
  ├── Service A
  ├── Service B
  ├── Service C
  ├── ...
  └── Service Z

Normally, every Eureka client sends periodic heartbeats.

Service A ── heartbeat ──→ Eureka
Service B ── heartbeat ──→ Eureka
Service C ── heartbeat ──→ Eureka

Now suppose there is a network problem between Eureka and many services.

Eureka suddenly stops receiving heartbeats from 70% of the services.

Eureka cannot know whether:

Those services actually crashed, or
There is a network problem preventing heartbeats from reaching Eureka.

If Eureka immediately removes all those instances, it could make the outage much worse.

What self-preservation does

When Eureka detects that the number of renewals has dropped significantly below the expected level, it enters:

SELF-PRESERVATION MODE

It becomes more conservative about removing instances.

Conceptually:

Expected heartbeats
        ↓
      1000
        |
        | Network problem
        ↓
Received heartbeats
        ↓
       300
        |
        ↓
Eureka detects abnormal renewal loss
        |
        ↓
Self-preservation mode
        |
        ↓
Avoid mass eviction

So Eureka essentially says:

"I may be seeing a network problem, so I should not assume that all these services are dead."

Example

Suppose Eureka has:

100 service instances

Normally, all instances continuously renew their leases.

Then a network partition occurs:

             Network problem
                   ↓
Eureka  X X X X X X X  Services

Eureka receives far fewer heartbeats.

Without self-preservation:

No heartbeat
     ↓
Remove instance
     ↓
Many instances removed
     ↓
Other services cannot discover them

With self-preservation:

No heartbeat
     ↓
Could be network problem
     ↓
Self-preservation
     ↓
Avoid mass eviction
Important interview point

Self-preservation does NOT mean Eureka knows that the services are healthy.

It means Eureka temporarily avoids assuming that missing heartbeats mean the instances are dead.

That's the key idea.

What happens to stale instances?

This is the trade-off.

If an instance has actually crashed but Eureka enters self-preservation mode, the stale instance may remain in the registry longer than desired.

Therefore:

Self-preservation
       ↓
Protects against mass eviction
       ↓
But may temporarily retain stale instances
One-line interview answer

Eureka self-preservation mode is a safety mechanism that prevents mass eviction of service instances when Eureka detects an unusually large drop in heartbeats, because the cause could be a network failure rather than actual service failures.

Remember this flow
Client registers
      ↓
Heartbeat / lease renewal
      ↓
Eureka monitors renewals
      ↓
Abnormally low renewals
      ↓
Self-preservation mode
      ↓
Avoid mass eviction

For your Eureka preparation, the next closely related topic is Eureka lease renewal and eviction, because self-preservation is based directly on the heartbeat/renewal mechanism.

1. Eureka Server Replication / Peer Awareness

In production, you generally don't want one Eureka Server to be the only service registry, because that would create a single point of failure.

You can run multiple Eureka Server instances.

             Eureka Server 1
                   ↕
             Eureka Server 2
                   ↕
             Eureka Server 3

These Eureka servers are called peers.

1.1 Why replication is needed

Suppose you have only:

        Eureka Server
             |
       Service Registry
             |
     All microservices

If Eureka Server goes down:

        Eureka Server ❌
             |
             X
      Service discovery

The discovery infrastructure becomes unavailable.

With multiple Eureka servers:

       Eureka Server 1
          ↕       ↕
          ↕       ↕
       Eureka Server 2
          ↕
       Eureka Server 3

If one server fails:

Eureka 1 → ❌
Eureka 2 → ✓
Eureka 3 → ✓

Clients can use the available Eureka servers.

1.2 What is peer awareness?

Peer awareness means Eureka Server instances know about their peer Eureka Servers and communicate/replicate registry information with them.

For example:

Eureka Server A
      |
      | peer communication
      ↓
Eureka Server B

If a service registers with one Eureka Server:

Payment Service
      |
      | register
      ↓
Eureka Server A

The registry information can be replicated to its peers.

Conceptually:

Payment Service
      |
      ↓
Eureka A
      |
      | replication
      ↓
Eureka B
      |
      ↓
Eureka C

Now multiple Eureka servers can have knowledge of the service instance.

1.3 Why is this useful?

Suppose:

PAYMENT-SERVICE

P1 → 10.0.0.10
P2 → 10.0.0.11

P1 registers with Eureka A.

Because of peer replication, the information can become available across the Eureka cluster.

        Eureka A
           |
      replication
           ↓
        Eureka B
           |
      replication
           ↓
        Eureka C

Therefore, the registry isn't dependent on only one Eureka Server instance.

1.4 Eureka clients can know multiple Eureka servers

A client can be configured with multiple Eureka server endpoints.

Conceptually:

Payment Service
      |
      ├── Eureka A
      ├── Eureka B
      └── Eureka C

If one Eureka server isn't reachable:

Eureka A ❌
Eureka B ✓
Eureka C ✓

the client can communicate with an available server.

2. What happens when Eureka is unavailable?

This is a very important interview question.

The answer depends on when Eureka becomes unavailable.

There are two important scenarios.

Scenario 1 — Eureka unavailable during application startup

Suppose:

Order Service
      |
      ↓
Eureka Server ❌

The Eureka Client may be unable to register/discover services at that moment.

The exact startup behavior depends on configuration and the application's discovery setup.

So you should not simply say "the application always stops."

Instead:

If Eureka is unavailable during startup, the client cannot register with or obtain fresh registry information from Eureka. Whether the application itself starts depends on the client's configuration and how the application handles service discovery.

Scenario 2 — Eureka becomes unavailable after the client has already discovered services

This is more interesting.

Suppose Eureka was working:

Order Service
      |
      ↓
Eureka
      |
      ↓
PAYMENT-SERVICE

P1 → 10.0.0.10
P2 → 10.0.0.11

The client has already obtained service information.

Now Eureka goes down:

Order Service
      |
      X
      |
Eureka ❌

The client may still have its previously obtained registry information/cache.

Therefore, service calls do not necessarily stop immediately just because Eureka is unavailable.

Conceptually:

Eureka
  ❌
   |
   X
   |
Order Service
   |
   ↓
Previously known Payment instances
   |
   ├── P1
   └── P2

This is one reason service discovery systems are designed with resilience in mind.

2.1 But what if a new instance starts?

Suppose Eureka is unavailable:

Eureka ❌

and a new Payment instance starts:

Payment-3

It may not be able to register successfully with Eureka while the registry is unavailable.

Therefore other services may not immediately discover:

Payment-3

The existing clients may continue using instances they already know about, depending on their cached discovery data and other configuration.

2.2 What if an existing instance dies?

Suppose the client has:

P1 → available
P2 → available

Eureka then becomes unavailable.

Later P1 crashes:

P1 → ❌
P2 → ✓

The client may still have P1 in its previously obtained registry information because it cannot currently obtain updated information from Eureka.

Therefore:

Cached information:
P1 → available
P2 → available

doesn't necessarily mean P1 is actually alive.

This is one reason you need timeouts, retries, circuit breakers, and other resilience mechanisms in a production microservices architecture.

2.3 Eureka outage does not mean all microservices immediately stop

This is a very important interview point.

A common incorrect answer is:

"If Eureka goes down, all microservices stop communicating."

That's not necessarily true.

A better explanation is:

Eureka unavailable
       |
       ↓
Existing discovery information may still be available
       |
       ↓
Existing service-to-service communication
may continue

But:

Eureka unavailable
       |
       ├── New registrations may fail
       ├── Fresh discovery information may be unavailable
       └── Stale instances may remain in local discovery data

So the impact depends on the timing, client behavior, cached registry data, and configuration.

3. Eureka's self-preservation concept

You should also know this at a 7–8 year experience level.

Eureka has a concept called self-preservation.

Imagine a network problem causes many clients to temporarily stop renewing their leases:

Network problem
      ↓
Many heartbeats lost
      ↓
Eureka sees many missing renewals

If Eureka immediately removed every instance, it could cause a large number of healthy services to disappear from the registry because of a temporary network problem.

Self-preservation is designed to reduce this kind of mass eviction during certain renewal-loss conditions.

Conceptually:

Temporary network problem
          ↓
Many renewals missing
          ↓
Eureka detects abnormal renewal loss
          ↓
Avoid aggressive mass eviction

This is an important resilience feature, but it also means that during certain failures, the registry can temporarily contain stale instances.

Eureka Caching

Eureka caching means keeping a local copy of service-instance information so that clients and servers don't need to query the network for every request.

There are two important caches to understand for interviews:

1. Eureka Client-side cache

A Eureka Client maintains a local registry cache containing information about available service instances.

Example:

Eureka Server
     │
     │ registry
     ▼
Order Service
(local Eureka cache)

PAYMENT-SERVICE
 ├── 10.0.0.1:8081
 ├── 10.0.0.2:8081
 └── 10.0.0.3:8081

Suppose Order Service wants to call Payment Service.

It generally does not ask Eureka for every HTTP request:

Order → Eureka → Payment

Instead:

Order
  │
  │ local registry cache
  ▼
10.0.0.1:8081
  │
  ▼
Payment Service

This reduces dependency on Eureka and network traffic.

2. Eureka Server-side cache

Eureka Server also has caching around the registry response it provides to clients.

Conceptually:

Eureka Registry
      ↓
Response Cache
      ↓
Eureka Client

When a client asks:

"Give me all instances of PAYMENT-SERVICE"

Eureka can serve the information from its response cache rather than constructing the response from the registry every time.

What happens when an instance goes down?

Suppose:

PAYMENT-SERVICE

Instance A → 8081
Instance B → 8082
Instance C → 8083

Client has cached:

A, B, C

Now Instance B crashes.

The sequence is roughly:

B stops
 ↓
No heartbeat
 ↓
Eureka lease eventually expires
 ↓
Eureka registry changes
 ↓
Clients refresh their registry
 ↓
Client cache becomes:
A, C

So cache refresh is not necessarily instantaneous.

For some period, a client may still have stale information.

Why is caching important when Eureka is unavailable?

This connects directly to your previous topic.

If Eureka Server goes down:

             ❌ Eureka
                │
                │
Order Service ──┘
     │
     │ local cached registry
     ▼
Payment Instance

The client may still know:

PAYMENT-SERVICE
 ├── 8081
 └── 8082

Therefore, existing service-to-service communication can often continue using the locally cached registry.

But:

New service registration can fail.
Registry updates cannot be obtained while Eureka is unavailable.
A newly started instance may not be discovered.
A dead instance may remain in the client's cache until the registry is refreshed.
